## 必学知识

- `【非常重点】可复现`：别人按照 README 能启动项目并重复评估。
- `【非常重点】指标有基线`：所有提升都要说明数据集、参数和优化前结果。
- `【非常重点】测试分层`：纯函数单测、数据库集成、Graph 路径测试和端到端测试各有职责。
- `【非常重点】技术取舍`：能解释为什么选择 LangGraph、Milvus、Redis 和当前模型。
- `【重点】诚实边界`：没有验证过的 QPS、准确率和生产规模不能写进简历。

## 必须交付的材料

1. 在线演示地址和演示账号说明。
2. GitHub 仓库与清晰 README。
3. 系统架构图和一次请求时序图。
4. API 文档和数据模型说明。
5. RAG Baseline 与优化后对比报告。
6. P50/P95、错误率和资源占用压测报告。
7. 三至五分钟演示视频。
8. 已知限制、安全设计和后续计划。

## 最终验收标准

- 后端格式、类型和测试检查通过。
- 前端 lint、类型检查、测试和构建通过。
- Alembic 迁移可从空数据库执行。
- RAG 评估可重复运行并保存原始结果。
- 在线环境完成核心演示流程。
- 不提交 `.env`、密钥、密码或测试用户隐私数据。

## 面试必答题

1. 你的 RAG 系统最初有什么问题，如何通过评估定位？
2. 为什么使用混合检索和 Reranker？
3. 如何保证答案引用真实可靠？
4. MySQL、MinIO、Milvus 部分失败时如何保证一致性？
5. LangGraph 在项目中解决了什么普通 Chain 难以解决的问题？
6. 如何防止跨用户数据泄露和 Prompt Injection？
7. 如果 QPS 增加十倍，先优化哪里？
