# 从普通 RAG 到可评估企业 RAG：P2-P4 学习指南

## 1. 这次升级解决什么问题

普通 Demo 常见流程是“整篇文档切固定长度 → 向量 Top K → 拼 Prompt”。它能演示，但有四个明显
缺陷：

1. 精确术语、编号、金额和专有名词可能被纯向量检索漏掉。
2. Chunk 太小缺少上下文，太大又引入噪声并增加 Token。
3. 检索分数不等于答案可信，版本变化后引用容易漂移。
4. 没有固定数据集、原始结果和消融，无法证明优化真的有效。

P2-P4 把问题拆成可单测和可替换的组件：

```text
安全摄取
→ 结构解析
→ 父子 Chunk
→ Dense + BM25 候选
→ RRF/Weighted 融合
→ Reranker
→ 父章节/相邻 Chunk 扩展
→ 发布版本复核
→ 固定来源 Hit
```

## 2. 四种检索模式

### Dense

把查询和 Chunk 编码为向量，按余弦相似度取候选。优点是能处理同义表达和语义改写，缺点是对
精确编号、缩写、金额和罕见词不一定稳定。模型名、revision、维度和归一化方式都属于索引
Profile，改变后应新建 Collection，不能原地混用。

### BM25 / Sparse

按词项频率和逆文档频率匹配。它非常适合制度编号、产品名、错误码和精确短语。中文效果依赖
Analyzer；所以本项目把“本地 BM25 流程测试”和“Milvus 原生 BM25 Analyzer 验证”明确分开。

### Hybrid

Dense 和 BM25 各自召回候选，再融合排名：

- RRF 使用名次而非不同量纲的原始分数，默认 `k=60`，通常更稳健。
- Weighted 先归一化分数，再按例如 Dense 0.65、BM25 0.35 加权，适合经过数据集调参的场景。

Hybrid 不是天然优于 Dense。只有固定评估集证明它没有明显回退并至少改善一个主指标，才应成为
默认策略。

### Reranker

召回阶段追求“不漏”，Reranker 对前几十个候选做更精细的 Query-Document 相关性判断，再选
Top K。它通常能提高前排质量，但会增加延迟和成本，所以必须同时看 nDCG、P95 延迟和失败降级。

## 3. 父子 Chunk 与上下文扩展

父子切分同时保存：

- Child：较短，负责参与检索和精确定位。
- Parent：章节级，负责补足解释上下文。

检索命中 Child 后，可以补充其 Parent 和同版本相邻 Child。扩展内容标记为 `context_only`，
不改变原始排名，也不重复计入 Recall 和 nDCG。这样可以避免“拿扩展后的大段正文冒充检索命中”
而虚高指标。

每个 Hit 固定到：

- `workspace_id`
- `document_id`
- `document_version_id`
- `chunk_id`
- `source_span_id`
- 页码或字符范围

回答历史因此不会随未来编辑而改变含义。

## 4. Query Rewrite 为什么必须可控

Rewrite 可把口语问题变成更适合检索的查询，也可生成少量同义查询提高召回。但它可能引入原问题
没有的实体或约束。因此本项目要求：

- 保留原查询。
- 最多增加两个改写。
- 只用结构化 `queries[]`。
- Query Rewrite 可单独关闭。
- 只有固定集 Recall@5 提升至少 0.02 才能默认开启。
- 文档中的提示词不能控制 Rewrite 或提升权限。

## 5. 为什么 MySQL 是事实源

一次上传会同时影响 MySQL、对象存储和向量库，但这三个系统没有真实的分布式事务。本项目采用：

1. MySQL 写版本、Job 和 Outbox。
2. Worker 幂等执行对象/索引副作用。
3. 发布前校验对象、Chunk 和向量数量。
4. MySQL 事务切换当前发布指针。
5. 失败写入补偿任务，稍后删除孤儿对象或停用向量。

Redis 只做通知和缓存；丢失后回退 MySQL 轮询。Milvus 可由 MySQL 已发布 Chunk 重建。搜索返回前
再次核对发布指针，可以阻止未发布或旧版本泄露。

## 6. 看懂评估指标

### Recall@5

Gold 来源是否出现在前 5 个结果。它回答“该找到的证据有没有找到”，适合检索门禁。

### MRR@10

只看第一个相关结果的位置。第 1 名命中得 1，第 2 名得 1/2，以此类推。它适合问答场景中
“正确证据是否尽早出现”。

### nDCG@10

同时考虑位置和多级相关性。强相关来源排在前面得分更高，适合评估 Reranker。

### 引用完整率

返回引用是否都属于本次授权 Hits，是否包含版本和 Source Span。它不是“答案事实正确率”，
但能防止模型编造不存在的来源 ID。

### 拒答指标

零证据问题应拒答。开发阶段先检查固定不可回答题的拒答召回；正式 P7 还要人工标注
Groundedness、答案覆盖和拒答 Precision/F1。

### 延迟

至少拆分 Query Rewrite、Dense、BM25、Fusion、Rerank、Context 和 Answer 时间，并报告 P50、
P95、机器配置、预热方式和数据规模。只报平均延迟没有面试说服力。

## 7. 合格判断

### 现在能证明的

- 代码质量、类型、单测和构建通过。
- 四格式解析、安全限制和父子切分纯函数通过。
- Fake/FIXTURE 环境中的租户隔离、版本复核、幂等和融合算法通过。
- 开发评估 Runner 能输出逐题原始数据和指标。

### 安装 Docker 并配置真实 Provider 后才能证明的

- MinIO 和 Milvus 真实协议、健康、持久化与故障恢复。
- Milvus 中文 BM25 Analyzer 和 Dense/Sparse Hybrid 的真实排序。
- 非 FIXTURE Embedding/Reranker 的 Recall、MRR、nDCG。
- 10k Chunk 下的 P95 延迟和资源消耗。

### P10 才能写进简历的

- 独立的 100 题人工标注集。
- 语料快照与盲测。
- 完整消融、失败案例和置信区间。
- 固定模型/Prompt/Embedding/Reranker/Chunk 参数。
- 原始报告可复现，且没有跨租户和旧版本命中。

## 8. 面试讲解顺序

建议按问题而不是按库名讲：

1. 为什么纯 Dense 漏精确词，所以加入 BM25。
2. 为什么两路分数不可直接比较，所以先使用 RRF，再用数据决定是否 Weighted。
3. 为什么小 Chunk 缺上下文，所以使用 Child 检索、Parent/邻接扩展。
4. 为什么外部存储不能事务提交，所以用 MySQL Outbox、幂等和补偿。
5. 为什么引用会漂移，所以固定发布版本和 Source Span，并在返回前复核发布指针。
6. 为什么“感觉更准”不可信，所以固定数据集、逐题 qrels、消融和原始报告。
7. 最后诚实说明当前已验证层级，以及 Docker、真实模型和 P10 盲测还缺什么。
